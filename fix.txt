The frontend architectural fixes (Points 1 through 14) have been implemented and validated. The remaining points below are related to the backend API architecture.

# 15. Your API is currently not a database-backed API

This is important.

The backend currently does:

```ts
const result: Config = config;
sendSuccess(..., result);
```

and `config` comes directly from:

```text
src/data/index.ts
```

So the current system is:

```text
TypeScript file
 ↓
object in memory
 ↓
JSON
```

There is:

```text
no database
no Redis
no persistence
no admin editing
no authentication
```

in the uploaded backend.

That is not inherently bad for the first version, but it means the "editable portfolio CMS" you described has **not actually been implemented yet**.

# 27. The "one-user registration" requirement needs a different design

Your backend currently has **no registration system**.

For what you described, I recommend:

```text
POST /auth/bootstrap
```

available only when:

```text
no admin exists
```

After the first account is created:

```text
registration permanently disabled
```

Database constraint:

```text
users.role = OWNER
```

and application rule:

```ts
if (existingOwner) {
  throw new ConflictError(
    "Owner account already exists"
  );
}
```

Do not implement this as:

```text
if (users.length === 0)
```

alone.

Two simultaneous bootstrap requests can race.

Use a database uniqueness constraint.

# 29. Google sign-in should not automatically create unlimited accounts

The Google callback should effectively do:

```text
Google identity
      ↓
Is this the configured owner?
      │

      │
      └── no → reject
```

Do not have:

```text
Google login
 ↓
new user
 ↓
database
```

for arbitrary Google accounts.

Your requirement is one owner.

# 34. Add optimistic concurrency

If you edit portfolio content from two browser tabs:

```text

Tab B
```

you don't want:

```text

```

Use:

```text

```

or another optimistic concurrency mechanism.

# 41. Don't ignore errors in production

You have:

```ts

process.exit(1)
```

Exiting after an uncaught exception is reasonable.

But you need proper structured logging before exiting and a process manager/platform to restart the process.

Render handles process restarts, but you still need observability.
